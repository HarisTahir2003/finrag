# Dependencies for a hosted Streamlit deployment (Streamlit Community Cloud and
# anything else that installs a requirements file rather than building an image).
#
# This file previously held `-e .[local,google,semantic,app,dev]` as a
# convenience for local installs. Streamlit Community Cloud requires a
# requirements.txt at the repository root and installs exactly what it finds
# there, so the name had to go to the deployment set. For a development
# environment use pyproject.toml directly, which is the source of truth either
# way:
#
#     pip install -e ".[local,google,semantic,app,dev]"
#
# tests/test_requirements.py asserts this file has not drifted from the
# base dependencies plus the [local], [app] and [groq] extras.
#
# ---------------------------------------------------------------------------
# CPU-only torch, and this is the line that decides whether the build succeeds.
# A plain `torch` requirement resolves to the CUDA wheel on Linux: 527MB
# declaring fifteen nvidia-* packages plus triton, onto a free tier with two
# cores and no GPU. It is the most common way a build like this dies.
#
# The "+cpu" local version identifier exists only on PyTorch's own index, so pip
# has to take it from there -- while still choosing the right wheel for the
# machine it is running on. An earlier version of this file pinned the wheel URL
# directly, which worked and was quietly architecture-locked: it named
# manylinux_2_28_x86_64, and resolving it on an aarch64 image failed with "not a
# supported wheel on this platform". Verified both ways on aarch64: the URL form
# fails, this form resolves 2.13.0+cpu with zero CUDA packages.
--extra-index-url https://download.pytorch.org/whl/cpu
torch==2.13.0+cpu

# push. `chromadb>=0.5` had already resolved to 1.5.9 -- a floor two major
# versions behind constrains nothing at all. Same idiom as the
# langchain-community ceiling below, which is load-bearing for its own reason.
